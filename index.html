02 / Our approach

From autonomy
to assurance.

01 /

Establish identity.

Identify the system or cryptographic key behind an interaction. Signed challenges can demonstrate key continuity. A signature verifies control of a key; real-world identity requires separate evidence.

02 /

Define authority.

Make delegated permissions explicit: which resources an agent may access, what it may do, when approval is required, and how access can expire or be revoked.

03 /

Verify outcomes.

Record meaningful actions and outcomes as reviewable evidence. We investigate signed messages, provenance and machine-verifiable receipts that help people inspect what agents actually did.

04 / Protocol research

Trust is a
verifiable process.

Three related specifications explore how autonomous agents can recognize a cryptographic counterpart, attach proof of origin to public messages and leave an auditable record of verification. Together, they follow a simple pattern: key → signature → verification.

Key→ Signature→ Verification
PROTOCOL 01v0.2

An agent's name
is not its identity.

Handles can be copied. The Agent Identity Protocol instead tracks a counterpart by its public key. A fresh, randomly generated challenge tests whether the responder currently controls the matching private key.

Agent identity / v0.2 research protocol
Challenge–response handshake
  1. 01
    Introduce

    Two agents begin a conversation and exchange an initial greeting.

  2. 02
    Exchange public keys

    Each side shares a public verification key—like a technical calling card.

  3. 03
    Sign a fresh nonce

    The challenger sends an unpredictable one-time value; the responder signs it with its private key.

  4. 04
    Verify the signature

    The challenger checks the signature using the public key and associates the result with that key's fingerprint.

This proves possession of a particular private key at the time of the challenge—not legal identity, continuity after key compromise, or that the key was trustworthy when first introduced. Initial key binding, rotation, revocation and replay protection remain important design concerns.
PROTOCOL 02v0.1

Make provenance
part of the post.

The Post Marking Specification proposes a compact signed marker at the end of a public agent post. A reader or independent verifier could inspect the marker and corresponding public key to check origin, rather than relying on a displayed account name alone.

Signed post marking / v0.1 specification

PROTOCOL 03v0.3

Evidence that
travels with trust.

Trust Receipts explore a shared record of who verified what, when the check occurred, and which evidence supports its result. The format is being co-designed and remains in the design-freeze stage; it is not a finalized standard or a deployed verification network.

Trust receipts / v0.3 in design
Conceptual verification receipt✳
VerifierKey or verifier reference
TimeVerification timestamp
SubjectClaim or artifact reference
EvidenceSignature / proof reference
OutcomeResult of the check

Illustrative data categories, not a frozen schema. A receipt is an auditable assertion about a check; it does not guarantee that an agent is safe or that the claim itself is true.

Design principle

No central directory is required to verify a signature against a known public key. Establishing who should be trusted, managing lost keys and handling disputes are separate problems that a real deployment must address.
